# 检查代码：正确性 / 风险 / 性能 → 对抗复核 → 修复 → 自动提交

目标（verbatim）：**检查代码，确保实现正确，无新增风险或性能回归。**

本 skill 是**通用**的改完复查工具，不假定任何技术栈或项目。流程闭环：

1. 定档（§0.5）：按改动量决定复查强度
2. 复查正确性 / 风险 / 性能
3. **按档位决定是否派发独立子 agent 做对抗复核**（专门推翻你的结论、找遗漏）
4. 综合两方结论，按**三态裁决**（确认问题 / 待验证 / 通过）
5. 能安全快修的必须修，修完只复检改动处，总轮次上限 2 轮
6. 通过则按规范自动提交（调用本 skill = 授权提交本次相关改动，无需再问）

## When to run

用户显式调用本 skill（如 `/verify-change-safety`），或说要检查近期改动是否正确、有无风险/性能回归时执行。

## Instructions

### 0. 项目约定自适应（通用化关键）

本工具不绑定任何具体项目。约定按以下优先级生效：

1. **仓库自有约定优先**：若仓库根存在 `AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md` 等贡献约定，遵循之（提交规范、分支策略、命名等）。
2. **规则目录优先（全局或项目级）**：项目级 `.cursor/rules/` 优先于全局 `~/.cursor/rules/`。
3. **无约定时退回内置通用项**：使用本文件第 2–4 节的内置检查。
4. **约定是补充，不是前提**：不要因为本项目没有某条规则就跳过对应的通用检查；规则缺失只意味着用通用标准判断，不意味着该项可免查。

**读规则的成本纪律（硬约束）**：

- 标了 `alwaysApply: true` 的规则（`post-edit-verification.mdc`、`minimal-change-scope.mdc`、`backend-guardrails.mdc`、`frontend-guardrails.mdc`）**已经在你的上下文里，不要再 Read 一遍**。直接按其内容执行。
- 只额外读**项目级** `.cursor/rules/` 中与本次改动技术栈相关的规则（前端改动读前端，不动后端就不读后端）。不要为了"确认约定"遍历整个 `.cursor/` 或 `docs/` 目录。
- 找不到项目级约定就按通用标准判断，**不要花轮次去找**。

### 0.5 复查强度分档（先定档，再动手）

| 档位 | 触发条件 | 执行 |
|---|---|---|
| **轻量** | 改动 ≤3 个文件 且 ≤100 行 且 不涉及鉴权 / 支付 / 数据迁移 / 并发 / 公共 API 契约 | §2–§4 主复查，**不派红队** |
| **标准**（默认） | 其它所有情况 | 主复查 + 红队 1 轮 |
| **深度** | 涉及鉴权 / 支付 / 数据迁移 / 并发 / 公共 API 契约，或 diff > 500 行 | 主复查 + 红队；第 2 轮是否开按 §5 条件判定 |

- 定档结论写成一句话放在输出开头（如「按轻量档复查（2 文件 / 34 行）」），让用户知道你走了哪档。
- 用户显式说「深度查」「全查」「仔细查」时无条件走深度档。
- 档位只影响**是否派红队**和**轮次上限**，§2–§4 的检查项一个都不能少。

### 1. 锁定复查范围

1. 用 git 确认改动：`git status`、`git diff`（含 staged）、`git log -n 8 --oneline`（看提交风格）。三条并行执行，一次拿全。
2. 范围优先：**本次需求相关的未提交 diff**。若工作区干净，只输出「无未提交改动」结论并结束，**不要**去拉 `origin/<base>...HEAD` 自我加戏。
3. `git diff origin/<base>...HEAD` **仅在用户明确要求复查已提交改动时**使用——它会把整个分支的改动拉进来，代价极高。
4. **大 diff 闸门**：若未提交 diff > 500 行 或涉及 > 10 个文件，先输出「文件清单 + 每个文件的改动意图」并等用户确认范围。不要把全量 diff 直接塞进后续步骤或红队 prompt。
5. 读清用户需求/验收点；没有则从最近对话与 commit message 推断。
6. 遵守最小改动原则：复查时不顺手大重构；修复仅限与发现问题直接相关的最小改动。

### 2. 正确性（通用）

逐项对照 diff：

- [ ] 是否满足需求与验收点（含边界：空值、失败回退、并发/重复触发）
- [ ] 调用链完整：导入、类型、前后端字段名一致
- [ ] 数据从哪来、展示/写入是否用对字段（警惕**同名但语义不同**的字段）
- [ ] 轻量/分页/按需加载路径下，关键展示字段是否仍可用（或已做批量补全）
- [ ] 构建/测试按 §2.1 分级执行，**不要跑全量**

> 示例（非强制，仅供理解"同名异义"陷阱）：某项目 `unit_no` 是集数、`generation_params.scene` 是分镜场号，二者不可混用。若你的项目有类似易混字段，重点核对。

### 2.1 构建与测试分级（硬约束）

按改动性质选**最低成本的一档，且只跑一次**：

| 改动性质 | 允许执行 | 禁止 |
|---|---|---|
| 纯文案 / 注释 / 日志字符串 / 配置值 | 不跑任何构建 | 任何构建或测试 |
| 类型 / 导入 / 签名 / 新增依赖 | 仅编译一次（Java `mvn -q -DskipTests compile`；TS `npx tsc --noEmit`；Go `go build ./...`） | 全量测试 |
| 存在精确覆盖改动文件的测试类 | 只跑这些类（如 `-Dtest=A,B`），一次 | `mvn test` / `npm test` / `pytest` 全量 |
| 改动文件本身就是测试代码 | 允许 `test-compile` + 跑该测试 | 全量套件 |

**硬禁止**（任何档位都不例外）：

- `mvn test`、`npm test`、`pnpm test`、`yarn test`、`gradle test`
- 无路径/`-k` 过滤的 `pytest`
- 非测试改动时的 `test-compile`
- watch 模式、起服务、起数据库、seed 数据
- 为"确认依赖语义"去读 `~/.m2` / `~/.gradle` / `node_modules` 里的库源码，或 `javap` / `jar tf` / `unzip` 反编译

构建超过 **180s** 直接中止，结果记为「未覆盖：构建超时」，不要重试、不要换命令再试。无法确定该跑什么时，**跳过并记入覆盖说明**，这比盲跑全量套件更有价值。

### 3. 无新增风险（通用 + 项目约定）

- [ ] **回归**：未改功能的调用方、筛选、展开/分页行为是否被破坏
- [ ] **项目约定**（若项目有则遵循，否则用通用底线）：
  - API 响应格式 / 鉴权约定（若有）
  - 后端：**长 I/O（网络/文件/外部调用/LLM）期间不要持有数据库连接或锁**（若项目用 DB）
  - 前端：业务请求走项目统一的 API 封装层（若存在）
- [ ] **安全**：敏感信息误下发/日志；XSS（如 React 文本 vs `dangerouslySetInnerHTML`）；密钥不入库
- [ ] **数据一致性**：是否误写 ORM 对象、是否覆盖已有正确字段
- [ ] **匹配条件是否过宽**（字符串 `in` / 宽松正则导致误匹配）

### 4. 性能回归（通用）

- [ ] 有无 N+1；列表场景是否改为**一次批量查询**
- [ ] 是否对已 `defer` 的大字段触发懒加载
- [ ] 是否对大 payload 做不必要的深遍历 / 全量 `JSON.stringify`
- [ ] 响应体是否无意义膨胀（轻量列表应只带标量白名单）
- [ ] 前端：有无多余请求、重渲染放大、大列表无截断导致的严重卡顿

空集合早退、按页 `IN (...)` 批量查，视为可接受；全表扫描或每行一查视为回归。

### 5. 对抗复核（按 §0.5 档位决定是否派发）

轻量档**跳过本节**，直接进 §6。标准/深度档派发一个**独立子 agent**（`verify-change-reviewer`）做对抗复核。

**给它的输入（必须内联，不许只给路径）**：

- **diff 正文直接贴在 prompt 里**——你已经拉过 `git diff`，把相关部分的原文贴进去。**不许**只丢一个仓库路径让它自己拉，那会让它白跑 `git status` / `git diff` / 重新 Read 一遍你已经读过的文件（实测第 1 轮有 26 次 Read 是在重建你的上下文）。
- 用户需求/验收点、你的初步结论（结论要写成可被反驳的断言，不要写成"看起来没问题"）。
- diff 过大（>800 行）时，贴**本次复查范围内的子集**，并说明被排除的文件和原因。

**必须原样写进 reviewer prompt 的硬边界**（否则它会跑偏成依赖库审计）：

- 只允许读**当前仓库内**的文件：diff 涉及的文件 + 它们的直接调用方。不要逐一重读整个模块。
- **禁止**：读 `~/.m2` / `~/.gradle` / `~/.npm` / `node_modules` 里的依赖源码或字节码；`javap` / `jar tf` / `unzip` 反编译；对 `$HOME` 或 `/` 做全盘 `find`；联网查第三方库文档。
- **禁止**跑构建、测试、起服务。构建已由主 agent 在 §2.1 完成，不重复。
- 它的战场是**本仓库内的数据流与调用链**，不是"第三方库语义是否正确"。库语义不确定时写进「需补充信息」，不要挖。

**轮次上限（第 2 轮默认关闭）**：

- 红队最多 **1 轮**。第 1 轮结论为「无推翻点」→ **直接进 §6，不跑第 2 轮**。
- 第 1 轮有推翻点、修复后，**默认也不再跑第 2 轮**，直接按 §7 复检改动处即可。在输出里写明「第 2 轮跳过：<N> 条推翻点 / 修复为局部逻辑」。
- 仅在以下任一条件成立时才允许第 2 轮，且**只针对修复处**，不重审整个功能：
  - 第 1 轮推翻点 **≥2 条**；
  - 或修复涉及**并发/竞态、鉴权、数据写入/迁移、公共 API 契约**。
- 第 2 轮后无论结论如何都停止，剩余分歧写进「待验证项」。

**隔离要求**：reviewer 必须用子 agent 工具独立派发，不共享本轮推理记忆。

**收到后**：吸收有效推翻点进入修复；对 reviewer 的误报逐条说明理由驳回，不要默默忽略。

**降级**：当前环境不支持派发子 agent 时，在同一 agent 内切换视角自证伪一次即可，不要反复自问自答。

### 6. 三态裁决

最终结论必须是以下三态之一，且各态有硬约束：

- **确认问题（confirmed）**：有具体证据 + 复现/触发路径。能安全快修则必须修。
- **待验证（needs_validation）**：缺某个事实，无法确定。必须写清：缺什么、怎么补（跑什么测试 / 问谁 / 看哪份文档）。**禁止在此态填写严重程度**——不确定 ≠ 低危。
- **通过 / 已修复后通过**：所有已知项已查且无确认问题。

**硬性约束**：综合风险评级不得超过已证明的实际影响；不可把「感觉严重」写成高危，也不可把「不确定」写成「没问题」。

### 7. 发现问题后（必须修复）

- 能安全快修：**先修，再只复检改动处**（重新核对修改的那几行 + 它们的直接调用方），**不要重跑一遍全流程**。
- **总循环上限 2 轮**（复查 → 修复 → 复检）。第 2 轮仍不通过，输出「确认问题（无法安全修）」并**停止**，把剩余问题交给用户决策。不要继续挖、不要无限刷。
- 修复范围遵守最小改动：只改与问题直接相关的代码；不顺手重构、不批量改名、不抽新抽象，除非用户明确要求。
- 不能本次安全修的：说明问题、影响、建议，结论标**确认问题（无法安全修）**，**不要当作已通过**，**不要提交**。

### 8. 通过后自动提交（强制）

当结论为**通过**或**已修复后通过**，且工作区仍有与本次需求相关的未提交改动时，**必须立即按规范创建 git commit**，不要询问用户是否提交。

提交步骤：

1. 并行执行：`git status`、`git diff`（含 staged）、`git log -n 8 --oneline`（参考近期 message 风格）。
2. 起草 commit message：
   - 若仓库有提交约定（`AGENTS.md` / `CLAUDE.md` / 既有 message 风格），遵循之。
   - 否则用通用约定：前缀 `Feat:` / `Fix:` / `Refactor:` / `Docs:` / `Chore:`（首字母大写），冒号后用简明中文或英文说明。
   - 示例：`Fix: 补全视频任务列表集数展示`、`Refactor: 抽离重复的去重逻辑`。
3. 只 stage 本次相关文件；**禁止**提交含密钥的文件（`.env`、`credentials.json` 等）；若用户改动里含此类文件，跳过它们并在输出中警告。
4. 用 HEREDOC 提交：

```bash
git commit -m "$(cat <<'EOF'
Fix: 简明中文说明。

EOF
)"
```

5. 提交后 `git status` 确认成功。
6. **不要** `git push`，除非用户另行明确要求。
7. 遵守 git 安全约定：不改 git config、不用 `--no-verify`、不 force push、不交互式 rebase；hook 失败则修问题后**新建** commit，不要 amend（除非用户规则中的 amend 条件全部满足）。

跳过提交的情形（仍须输出复查结论）：

- 工作区干净，无可提交改动
- 结论为**确认问题**
- 仅含不应提交的敏感文件且无其它可提交改动

### 9. 输出格式（三态）

简洁回复，结构如下：

```markdown
复查结论：**通过 / 已修复后通过 / 确认问题(已修待复检) / 确认问题(无法安全修) / 待验证**
档位：**轻量 / 标准 / 深度**（<文件数> 文件 / <行数> 行 / 红队：跳过·1 轮·2 轮；跳过第 2 轮时注明原因）

**正确性**
- …

**风险**
- …（无则写「无明显新增风险」）

**性能**
- …（无则写「无性能回归」）

**对抗复核**（轻量档写「已跳过：轻量档不派红队」）
- reviewer 推翻点 + 你的采纳/驳回理由
- reviewer 认同的部分（若有）

**已做加固**（若有）
- …

**提交**
- 已提交：`<short-sha> <message>` / 已跳过：<原因> / 未提交：确认问题

**待验证项 / 已知限制**（非回归，若有）
- …

**覆盖说明**
- 正确性：已查 / 未覆盖：<原因> / 跳过：<缺信息>
- 风险：已查 / …
- 性能：已查 / …
- 构建：<跑了什么 / 跳过原因>
```

不要复述大段无关代码；只报告与结论相关的证据。

## Examples

**例 1：轻量档，不派红队**

1. 定档：改了 1 个文件的日志参数、7 行 → 轻量档。
2. §2–§4 主复查通过，按 §2.1 跳过构建。
3. 直接提交，输出「通过」+ 档位说明 + 无红队。

**例 2：标准档，有问题 → 修复 → 红队认同 → 提交**

1. 定档：4 个文件 / 120 行 → 标准档。
2. 发现某列表缺字段补全 → 修成批量查询。
3. 派红队 1 轮，红队认同并补一个边界遗漏 → 吸收修复，只复检改动处。
4. 复检通过，自动 `git commit`，输出「已修复后通过」。

**例 3：深度档，红队推翻 → 无法安全修**

1. 定档：改了鉴权中间件 → 深度档。
2. 主结论通过，红队指出一处并发竞态、附证据链。
3. 主 agent 确认成立但无法最小安全修复。
4. 输出「确认问题(无法安全修)」+ 问题/影响/建议，**不提交**。

**例 4：工作区已干净**

1. `git status` 显示无未提交改动 → 直接输出「无未提交改动，无需复查」，**结束**，不要去拉分支 diff。
